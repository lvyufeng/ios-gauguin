# gauguin / iOS 16 — session handoff (2026-11-03)

Read `NOTES.md` for the full engineering log. This file is the short version:
what changed, **what is proven vs what is only reasoned**, and the exact next
action when a phone is available.

## TL;DR

The boot stops inside `sweet_keys_init()`. That is measured, not guessed
(below). Everything else on the path has been checked against the phone's own
device tree or against a boot log that reached `exec launchd`.

**Nothing in this session was verified on hardware.** The phone dropped off
USB during the first `sweetlog=0` experiment and has not re-enumerated on
either host since (checked every round).

## What is proven

**The stall is in `sweet_keys_init()`.** Diffing a failing boot against
`.deps-cache/logs/boot-journaled-userland.txt` (a boot that reached
`BSD root: ufsroot0` and launchd) step by step:

| # | working boot | failing run |
| --- | --- | --- |
| 1–10 | … | identical |
| 11 | `SWEET UFS: keys_init` | `SWEET UFS: keys_init` |
| 12 | `SWEET KEYS: arb=0x50010000 apids=512 …` | **nothing** |
| 13–17 | `keys_init done`, `touch_init`, `usb_probe`, `init complete` | — |

Everything before that line is byte-identical, including `dlil_init`,
`bsd_autoconf`, `rootdev called` and `init reg`.

## What changed (16 commits, `d7ae8f1`..`7c85c51`)

| commit | change | why |
| --- | --- | --- |
| `d7ae8f1` | TLMM `0x03900000` -> `0x00f100000`; ADT emits `qcom,sm7225` | **the phone is SM7225, not SM7125.** `0x03900000` is SM7150's pinctrl and is unmapped here - that is the "stops after stage D: map TLMM" seen repeatedly on 10-23 |
| `9d48850` | one UFS request slot per writer (main / log / mark), own UCD + buffer + lock each | every command used slot 0; the log thread's first flush ran while init still held it |
| `0e84990` | touch bring-up on its own thread | it ran inline on the thread that must return before BSD mounts root |
| `5f117da` | init sequence restored to the order that provably booted | an earlier entry wrongly diagnosed the init `sweet_log_sync()` calls as deadlocking; the working log shows them running fine |
| `187e5c2` | boot line = the working one: `debug=0xc cpus=1 … sweetlogms=200` | no boot that mounted the root ever used `cpus=8`; `0xc` keeps panic text |
| `763e732` | atomic command tags | splitting slots made concurrent callers real, and `++su.tag` is not atomic |
| `c08f46f` | two `sweet_log_sync()` calls restored around `keys_init` | they were missing, so `keys_init()` ran with no flush either side |
| `af483d1` | `keys_read()` deadline-bounded (50 ms), every init step marked | the PMIC poll could park the init path for seconds |
| `9455704` | `sweet_log_mark_sync()` writes marks from the caller | marks were flushed only by the log thread - useless precisely when init is stuck |
| `f2dcc82` | `dsb osh` -> `dmb osh` in `keys_read()` | a DSB waits for *all* outstanding accesses; if SPMI stalls the barrier itself never returns, and the deadline sits *after* it |
| `226b715` | marks built with byte stores, no 4 KiB `memset` | 11 marks in `keys_init` |
| `41f3889`, `32563ee`, `1c423fd`, `7c85c51` | audits (below) | |

## Audits done offline

- **All 9 hardware base addresses** match the phone's device tree (from the 137
  backup's `dt/`): GCC `0x100000`, SE8 `0x988000`, TLMM `0xf100000`, SPMI
  core/cnfg/obs `0xc440000`/`0xc40a000`/`0xe600000`, DWC3 `0xa600000`, QUSB2
  `0x88e3000`, UFS `0x1d84000`.
- **Every `ml_io_map()` window** covers the highest offset the code reads.
- **DMA layout** of the UFS allocation: no overlaps; the whole boot path uses
  1.55 MiB of the 8 MiB arm `IO_MAP_SIZE` (19%).
- **ADT vs payload**: `dram-base 0x180000000`, `dram-size 0x100000000`,
  `dram-base-low 0x80000000` - consistent in both.
- **USB gate logic** matches the register values in the working log
  (`GDSC` bit31 set, all CBCRs bit31 clear), so `sweetusb=0` is **not** a valid
  workaround - that advice is from before the register map was corrected.
- **PMIC topology is stable**: every working log reports
  `arb=0x50010000 apids=512 pon-apid=308 gpio-apid=366`.
- **The binary, not just the source**: `_keys_read` disassembles to `dmb osh`
  followed by a loop with all three exits (done bit, deadline, 1000 iterations).

## Rule kept from earlier sessions, still worth repeating

Always check the `Darwin Kernel Version` banner in a pulled log against the
image's own banner before believing anything in it. `fastboot-cycle.sh` does
this and exits 3 on a stale log.

## The next action

```
adb devices          # if empty, the phone needs a manual recovery first
tools/bisect-keys.sh # ~2 minutes, runs both images, prints the verdict
```

If `adb` shows nothing: a **full power-off (hold power 15 s), 10 s wait, then
cold boot into TWRP** is what cleared the bootloader's reboot-loop protection
before. If that does nothing either, the phone is likely flat - charge it 30
minutes and retry. Only after that is hardware/EDL worth considering.

The verdict from `bisect-keys.sh` says which of three worlds we are in:

1. `sweetkeys=0` gets past `keys_init` and the default does not → the stall is
   the PMIC/keys path, and the marks in
   `research/tmp/bisect/on.marks.txt` name the exact step.
2. Both get past → the stall is later (touch or USB); the marks say which.
3. Neither gets past → the boot-arg is not the difference. If both stop on the
   same mark, the blame moves back to the UFS/log machinery or to something
   before `sweet_keys_init()`, which would make some conclusions above wrong.
